# Задачи после приёмки 1.5b: каталог и control-WSS

**Статус на 2026-10-17:** RE-18 в работе: клиент и аппаратные замеры готовы,
остались проверки авторизации и сетевого отказа. RE-19 открыта; её реализация
не начиналась.
**Основание:** владелец подтвердил, что ожидание каталога и восстановления управления после обрыва WSS мешает в обычном использовании (2026-10-16). Эти работы не входят в завершённый план UI/аудио.

## RE-18 — ускорить REST-запросы каталога после простоя

**Исходная проблема.** `rock_http_request()` создавал и уничтожал
`esp_http_client` для каждого запроса, поэтому TLS-сессия не переживала
запрос. В `telemetry/uc15b_bench.log` одна загрузка каталога занимала около
2,1 с от начала fetch до HTTP 200; это был одиночный замер. Через этот wrapper
идут поиск, страницы каталога и запросы авторизации.

**Текущий статус.** В `2c318d2` добавлены постоянный REST-клиент,
сохранение TLS-сессии, очистка состояния между запросами и восстановление
после закрытого keep-alive. Аппаратные замеры вынесены в
[`re18-acceptance.md`](re18-acceptance.md). Приёмка остаётся незавершённой:
принудительный 401, применение сервером актуального/отсутствующего bearer и
управляемая сетевая ошибка не проверены.

**Результат.** Повторные REST-запросы к тому же origin используют открытое соединение, когда оно пригодно, либо сохранённую TLS-сессию после его закрытия. Холодное подключение и отказ сервера принять ticket работают штатно. Клиент источника аудио из 1.5b остаётся отдельным владельцем своего handle.

**Границы работы:**

- Установить фактических вызывающих `rock_http_request()` и закрепить одного владельца клиента либо сериализацию обращений; не вводить общий пул соединений без необходимости.
- Включить сохранение TLS-сессии для REST handle. При повторном запросе правильно сбрасывать состояние ответа, метод, POST body, `Content-Type`, bearer и `user_data` обработчика. Не переносить Authorization на запрос без bearer.
- Сохранять клиент только для того же scheme/host/port; при смене origin, ошибке транспорта или некорректном ответе безопасно пересоздавать его.
- Сохранить существующие правила 401 → обновление токена → один повтор, лимиты ответа и таймауты. Не писать токены, URL с секретами или тело ответа в лог.

**Приёмка на плате:**

1. Снять базу и результат для холодной загрузки, 5 повторных загрузок и загрузки после 5–10 минут простоя на одной сети. Логировать отдельно время connect/TLS, ожидание заголовков и полный путь от действия пользователя до отображения страницы. Подтвердить принятие ticket TLS-диагностикой либо сопоставимой трассой. Для повторного запроса с принятым ticket целевой ориентир — медиана каталога ≤1 с на том же стенде; холодный путь не должен ухудшиться существенно. Отказ/истечение ticket фиксировать отдельно, не выдавать за регрессию resumption.
2. Проверить browse, поиск, следующую страницу, запрос после обновления bearer и штатный 401-повтор. Проверить, что сервер видит актуальный bearer, а анонимный запрос не получает прежний заголовок Authorization.
3. Проверить восстановление после закрытого сервером keep-alive и после сетевой ошибки. Повторный запрос должен либо завершиться, либо дать существующую ошибку UI без зависания; после него следующий запрос работает.

## RE-19 — сократить окно без управления при переподключении control-WSS

**Проблема.** `rock_ws_stop()` уничтожает WebSocket-клиент, а `rock_ws_start()` создаёт новый. После обрыва управление восстанавливается через новое TLS-соединение и повторную регистрацию. Используемый `esp_websocket_client_config_t` не предоставляет прямого параметра сохранения TLS-сессии, аналогичного HTTP-клиенту; перенос 1.5b строка в строку невозможен. Пока нет приёмочного разложения полного времени переподключения по сегментам.

**Результат.** При доступной сети повторный control-WSS connect использует TLS resumption, если сервер принимает ticket. Если ticket истёк или отвергнут, происходит обычный полный handshake без зацикливания. После подключения проходят hello, регистрация, восстановление состояния и heartbeat; команды снова исполняются.

**Границы работы:**

- До выбора реализации замерить `обнаружение обрыва → начало reconnect → TLS/WebSocket connected → registered/управление доступно`, отдельно для разрыва сокета при работающем Wi-Fi и потери Wi-Fi с восстановлением IP. Оптимизировать TLS, только если он заметно влияет на пользовательскую паузу; если доминирует обнаружение обрыва или backoff, скорректировать решение по этим данным.
- Исследовать поддерживаемый `ext_transport`/API компонента для сохранения TLS-сессии. Если нужен патч managed component или собственный транспорт, оценить сопровождение и выбрать минимальный поддерживаемый вариант до реализации.
- Сохранять ticket только для того же origin; обновлять Authorization при каждом подключении. Сохранить проверку сертификата, обработку close/error, защиту heartbeat и повторную синхронизацию состояния.
- Не связывать WSS ticket с отдельным клиентом station-прокси и не менять протокол RockServer ради этой задачи.

**Приёмка на плате:**

1. На том же стенде выполнить не менее 5 циклов обрыва WSS при работающем Wi-Fi и 5 циклов потери/возврата Wi-Fi. Сравнить медианы и разброс каждого сегмента до и после. Для прогретого соединения целевой ориентир — сократить `WSS start → connected` минимум вдвое; отдельно показать полное время `обрыв → команды снова работают`.
2. Подтвердить фактическое принятие ticket сервером по TLS-диагностике либо сопоставимой трассе, а не только по признаку переиспользованного handle. Проверить отказ/истечение ticket, неуспешную авторизацию и смену токена.
3. После каждого reconnect отправить одну команду и убедиться в корректном `command.result`, состоянии плеера и heartbeat ACK. Во время теста звук не должен прерываться из-за control-WSS, если Wi-Fi продолжает работать.

**Порядок:** RE-18 даёт более узкое изменение и быстрый пользовательский выигрыш. RE-19 следует выполнять после замера полного reconnect; задача не зависит от реализации RE-18 и может планироваться отдельно.
