Калибровка порога (прямой отправкой на rockplatform.win): реальная речь
rms 855/430/215 — распознаётся во всех трёх уровнях; SNR важнее абсолютного
уровня. Плата после фиксов: пол 176 (×2 как ожидалось), 0 ложных wake за

**Живая верификация 27.10 13:51–14:30 (после всех фиксов, 40 мин лога):**
два wake-пересечения на живую речь (score 0.831/0.729), обе сессии прошли
до полных транскриптов бытовой речи («У тебя все штаны…», «Как ее зовут»,
RMS 1573 — усиление 36 дБ видно), интерпретатор корректно отклонил
не-команды. Ложных wake в тишине 0. Конвейер wake → захват → STT →
интерпретация работает на живом голосе; исполнение реальной команды
владельцем («Роксервер стоп/рок») — осталось произнести при активном
логгере для финальной записи. Известная особенность v5: детектор сработал
на обычной речи с высоким score — ложные срабатывания на музыке/речи
остаются треком v6 (дальше/назад — см. manifest-заметку выше).

**Вечер 27.10 — «всегда Не удалось разобрать команду» (state 14).** LLM-провайдер
проверен напрямую с прод-ключом — жив. Измеренная причина: сессии wake-пути
коммитились по «1 с тишины после последней речи», где последняя речь —
wake-слово из preroll; при паузе ≥1 с между «Роксервер» и командой захват
обрезался до одного wake-слова. Дальше: срезка wake-слова давала пустую
строку → `intent_resolution_failed` (state 14); до срезки тот же транскрипт
давал LLM→unknown → state 7 («слышит, но не поддерживается»). Логгер
подтвердил: транскрипты-обрывки («Открой твой гепси лейк») и
speech_not_recognized. Фикс в прошивке (`rock_voice.c`,
`capture_utterance`): при наличии preroll коммит невозможен раньше
preroll+3 с живого захвата — команда успевает попасть в сессию. Серверное
смягчание (транскрипт = только wake-слово → «Уточните команду», state 6)
закоммичено локально `dfdc47b`, НЕ задеплоено (ждёт согласия владельца).

## Исходная неисправность и диагноз

Плата отвечала «Команда не поддерживается» на все голосовые запросы.
Протокол и пайплайн команд оказались исправны: записанная живым голосом
команда «Роксервер стоп» исполнялась дважды (serial-триггер и wake+preroll,
`device.command` → `command.accepted` → state=4). Причина была в серверной
интерпретации транскриптов, измерено два режима отказа:

1. `intent_resolution_failed` (экран «Не удалось разобрать команду», state 14):
   LLM-провайдер (Yandex) отвечал ошибкой примерно в каждой второй сессии, а
   детерминированный fallback срабатывал только при точном совпадении узкого
   словаря токенов в транскрипте.
2. `unsupported_intent` (экран «Команда не поддерживается», state 7): LLM
   возвращал `unknown` на валидные команды; на verdict `unknown` fallback не
   предусматривался вовсе. Отдельный измеренный случай: STT склеивает
   wake-слово с командой — транскрипт «Роксерверрок» без токена «рок» —
   из-за этого поиск «Роксервер рок» всегда падал в `unsupported_intent`.

Транскрипты стали видны после добавления в прошивку логирования финального
`transcript`-фрейма (`rock_voice.c`, печатается как
`rock-voice: final transcript "…"`; сервер транскрипты сознательно не
логирует).

## Исправления (rockserver, задеплоено на rockplatform.win)

- `d0b7f6e` — rescue детерминированным классификатором при verdict `unknown`
  (при наличии базового командного токена) и расширенный словарь outage-fallback:
  старт/продолжи (resume), лайк/избранное (add_favorite), громче/тише
  (volume_change ±5) вместе с прежними стоп/жанрами. «Какая погода» по-прежнему
  не превращается в радио.
- `61d8dcc` — срезание произнесённого wake-слова («роксервер», «рок сервер»,
  «рок-сервер», включая склейки) перед интерпретацией и ранжированием в
  device-ветке; в result-фрейме echoed оригинальный транскрипт.
- Проверки: cargo fmt, строгий clippy, cargo test (287) — зелёные; оба деплоя
  `readiness=passed`, `yandex_keys=4`. Попутно задеплоено и находившееся в
  дереве уточнение ранжирования `85c9259` (classified search filters).

## Измеренная верификация на плате (TTS через динамики ПК, COM6)

- «Роксервер стоп» → `final transcript "Роксервер стоп"` → `intent=stop
  status=succeeded` (state 4), воспроизведение остановлено.
- «Роксервер старт» / «громче» → команда исполнена через command pipeline
  (state 4). «громче» поднял громкость 15→20 — возвращено CMD:UI:VOL-; перед
  пробами громкость всегда проверять ≤15.
- «Роксервер рок» (транскрипт «Роксерверрок») → `voice search autoplay
  results=10` → автозапуск первой станции через Cast, playback=2 при 15%.
- Остающиеся режимы (закономерные или открытые):
  - «дальше»/«назад» → `capability_not_supported`: в manifest прошивка
    объявляет только play/pause/stop; потребуется firmware-манифест с
    next/previous.
  - «лайк» без играющей станции → `station_not_found` (по конструкции).
  - Один срыв «тише»: result со статусом failed без доставки `device.command`
    на плату — единичный случай, требует отдельного расследования при
    повторении.
  - Команды поверх громко играющего Cast: микрофон платы слышит музыку, STT
    расшифровывает текст песни (измеренный транскрипт «Роксер является чувство
    вины…») → `unknown` → state 7. Кандидат на фикс — пауза Cast на время
    voice-сессии (для локального плеера пауза уже есть,
    `rock_voice_release_pause`).
  - «старт» из полностью остановленного состояния исполняет команду, но плеер
    не возобновляет воспроизведение (firmware-side поведение resume).

## Следующие шаги

1. Живая проверка владельцем: произнести «Роксервер стоп/старт/рок/громче/
   тише/лайк» — фоновый serial-логгер (tools-скрипты `artifacts/serial_logger.py`)
   захватит транскрипт, intent и код ошибки каждой пробы.
2. При повторении сбоя «тише» (failed без device.command) — снять полный лог
   control-WS и завести отдельный тикет.
3. Решить по UX: пауза Cast на время голосовой сессии; manifest next/previous;
   resume из остановленного состояния.
4. Качество wake (ложные срабатывания на музыке: 19 crossings за ~30 минут
   игры против 0 в тишине) — отдельный трек v6 (файлы v6 уже в дереве).

  повторная попытка STT, но это инфраструктурная проблема, не кодовый баг
  интерпретации.
- Итог: интерпретация команд исправлена и держится при искажённых
  транскриптах; остаточная нестабильность сосредоточена в доступности
  Yandex SpeechKit/LLM.
