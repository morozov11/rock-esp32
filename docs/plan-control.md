# Центр управления: RockCast-радио на ESP32

Этот файл — точка возобновления и центр координации. Диалог, созданный
2026-09-09, назначен владельцем центром управления выполнением плана
[`rockcast-device-plan.md`](rockcast-device-plan.md). Задачи по всем связанным
репозиториям (rockserver, rockmobile, rockcast) отправляются отсюда. Любой
новый сеанс начинается с чтения этого файла и текущего плана.

## Контекст аудита 2026-09-09 (сжатые находки)

Аудит первого варианта плана против фактического кода rockserver/rockmobile.
Каждая находка закрыта соответствующим шагом или задачей плана.

- **F1.** `station.play_stream`-резолюция существует только как planned-контракт
  в OpenAPI: роутер форвардит `station.play_station` без изменений, разрешения
  station→stream в коде нет. → шаги 2.3, 3.2 (RS-3).
- **F2.** Каталог: `GET /api/v1/catalog/stations` реализован, но отсутствует в
  OpenAPI; browse и search анонимные и возвращают `stream_url`. → шаги 2.1,
  3.1 (RS-1, RS-2).
- **F3.** Voice `/voice/stream` — анонимный поиск станции по транскрипту;
  типизированный `UserIntent` есть, но к voice не подключён; cancel-фрейма
  нет; OpenAPI дрейфует (sample rates, лимиты сессии). → шаги 2.5, 3.3
  (RS-1, RS-4).
- **F4.** Rockmobile: нет UI, отправляющего `station.play_station`; `media.volume`
  жёстко валидируется (min 0 / max 100 / step 1..100, нарушение ломает весь
  снапшот каталога); клиентский deadline 10 с с пометкой Expired. → шаг 5
  (RM-1), фиксация семантики «accepted сразу / result асинхронно ≤30 с» в
  шаге 4.5.
- **F5.** Физическая приёмка DC-018 не закрыта: golden presentations,
  координаты тача после power cycle, offline-переходы. → шаг 6.0 (RE-1).
- **F6.** `esp_audio_codec` ≥ 2.6.0 требует чип ESP32-P4 ≥ 3.0, плата — v1.3.
  → спайк и пин версии в шаге 1.2 (RE-3).
- **F7.** `esp-sr` поддерживает ESP-IDF 6.x только с v2.4.1 и экспериментально.
  → спайк и пин версии в шаге 1.3 (RE-3).
- **F8.** Партиции: factory 3 МиБ без OTA-слотов, бинарь 1.8 МиБ, из 16 МБ
  флеша задействовано ~3 МБ; OTA отсутствовал во всём плане. → шаг 1.1
  (RE-2), шаг 9 (RE-9).
- **F9.** Wi-Fi-онбординг конечного пользователя отсутствует (ssid/пароль в
  sdkconfig — дев-конфигурация). → шаг 9 (RE-9), по умолчанию в скопе.
- **F10.** Ранжированный search на сервере не курсоруется — единый курсорный
  путь был бы новой серверной разработкой. → решение: два пути (шаг 2.1).
- **F11 (найдено при выполнении RE-2, 2026-09-09).** Физический pairing на
  плате никогда не завершался: namespace `rock_auth` в NVS отсутствует (и до,
  и после перепрошивки), живая верификация DC-017 покрывала только Wi-Fi-сканер
  и C6; pairing/WSS подтверждены лишь host-тестами. Локальный sdkconfig без
  Wi-Fi-учёток и `CONFIG_ROCKSERVER_BASE_URL`. → задача RE-11; формулировка
  README поправлена.
- **F12 (найдено при выполнении RE-3, 2026-09-09).** Данные моделей esp-sr
  пакуются в отдельный `srmodels.bin` под партицию `model`, которой нет в
  таблице RE-2 (весь флеш отдан под ota_0/ota_1). RE-8 обязан выбрать:
  урезать OTA-слоты под партицию `model`, встроить модели в app-образ или
  внешний путь (`ESP_SR_EXTERNAL_MODEL_PATH`). Решение влияет на схему
  партиций — чем раньше принято, тем дешевле миграция. → задача RE-8
  (решение), потенциально правка RE-2-таблицы.
- **F13 (найдено при выполнении RE-4, 2026-09-09).** Динамик физически не
  подключён к плате: воспроизведение подтверждено только электрически
  (I2S TX + ES8311 + PA); «акустическая петля» из первого отчёта оказалась
  музыкой в комнате и отозвана исполнителем до приёмки. Акустическая
  приёмка шага 1 (слышимый тон) и замер акустической связи mic↔динамик
  для AEC (нужен RE-8) открыты. → задача RE-12, заблокирована физическим
  подключением динамика владельцем.

## Журнал решений

- **2026-09-17, центр управления.** RC-4/RM-4 реализована локально во всех трёх
  репозиториях по ТЗ с UX-ревизией **Station-First** (единый каталог → экран
  станции с селектором устройства вывода; решение владельца 2026-09-17: паузы
  нет — только play и stop, `playback.pause` не рекламируется и не показывается
  по capabilities). RS-8 (rockserver): `DeviceControlDirectoryEntry.runtime_state`
  (owner-scoped, гейт `entity.state.read`, absent-семантика), golden snapshot +
  новая upsert-фикстура, `cargo test` 211/0 (+15 ignored gated). RC-4 (rockcast):
  truthful publisher — полные статусы `buffering/playing/stopped/error`
  (Idle после запуска = stopped), точный `station_id` сохраняется в error/stopped,
  монотонная персистентная ревизия, `cargo test` 129 unit + 2 integration /0.
  RM-4 (rockmobile): `LivePlaybackReducer` (полная матрица §4.4: без optimistic
  UI, внешнее переопределение сбрасывает intent немедленно, drag-изоляция
  громкости, commit-on-release), `StationPlayerScreen` (hero, `Играть на: [...]`,
  ● В ЭФИРЕ без seek/таймлайна, capability-driven transport), `LiveMiniPlayer`,
  fallback «Станция <id>»; `testDebugUnitTest` 129/0 (15 reducer-тестов),
  `lintDebug` чисты. Физическая USB-приёмка (Phase 4) не выполнена и не
  заявляется. Без изменений: station-путь только `play_station` → серверный
  `play_stream`, без новых endpoints, без raw stream URL, Cast/relay до RS-7.

- **2026-09-17, центр управления.** После физически принятой RC-3 создана
  отдельная planned-задача RC-4/RM-4: выбранная на Mobile станция подтверждается

- **2026-09-17, центр управления.** Живая проверка RC-3: на USB-подключённом
  RockMobile 0.1.6 открыт экран «Устройства»; после запуска текущего локального
  release-бинаря RockCast и ручного refresh directory парный Windows-таргет остался

- **2026-09-17, центр управления.** RC-3 закрыта живой приёмкой. Причина
  `offline` установлена без ослабления auth: native-session и `protocol.welcome`
  проходили, но сервер возвращал `registration_rejected`, так как в durable store
  уже был другой manifest с revision 2. RockCast повысил revision до 4, после
  чего Windows-таргет стал `В сети` в refresh directory USB-подключённого
  RockMobile. Промежуточная `relay.stop` не является приёмочным результатом:
  текущий RockServer считает relay/Cast-команды unknown (RS-7 pending), поэтому
  RockCast перестал рекламировать эти capabilities до серверной реализации.
  В RockMobile добавлена видимая стандартная `Остановить`; одна
  `playback.stop` на явно выбранном online RockCast завершилась сообщением
  «Состояние плеера подтверждено.». Проверки: RockCast `cargo test
  device_control --lib` 17/17, release rebuilt; RockMobile `:app:installDebug`
  успешно установлен на RMX5056.

## Правила выполнения и приёмки

- Контракт перед реализацией: RS-1 закрывается до RS-2/RS-3/RS-4.
- rock-esp32: сначала host contract tests (`tests/device_control_contract.rs`)
  и серийная сборка `idf.py`; флеш только после успешной сборки; перед прошивкой
  заново детектить COM-порт; физическая верификация записывается в
  `docs/*-progress.md`.
- rockserver: контрактные тесты, включая `tests/openapi_contract.rs`; после
  реализации — обновить `docs/roadmap/device-control-tasks.md`, `docs/status.md`,
  `docs/tasks.md`.
- rockmobile: сборка + ручной сценарий на физическом ESP32.
- Сквозное правило: никаких секретов, токенов, аудиосэмплов и stream URI в
  логах, коммитах и документах.
- Манифест устройства честный: capability добавляется только после прохождения
  приёмки соответствующим обработчиком на железе.

## Как диспатчить задачу из центра

Исполнителю (суб-агенту в целевом репозитории) передаются:

1. ID задачи и репозиторий (путь).
2. Соответствующий шаг плана `rockcast-device-plan.md` и находки аудита (F#).
3. Приёмка шага как критерий готовности.
4. Требование по завершении: коммиты в целевом репо, записи в его docs,
   отчёт центру управления (что сделано, что проверено, что осталось).

Статусы на доске обновляет центр управления, не исполнитель.
