# Центр управления: RockCast-радио на ESP32

Этот файл — точка возобновления и центр координации. Диалог, созданный
2026-09-09, назначен владельцем центром управления выполнением плана
[`rockcast-device-plan.md`](rockcast-device-plan.md). Задачи по всем связанным
репозиториям (rockserver, rockmobile, rockcast) отправляются отсюда. Любой
новый сеанс начинается с чтения этого файла и текущего плана.

## Контекст аудита 2026-09-09 (сжатые находки)

Аудит первого варианта плана против фактического кода rockserver/rockmobile.
Каждая находка закрыта соответствующим шагом или задачей плана.

- **F1.** `station.play_stream`-резолюция существует только как planned-контракт
  в OpenAPI: роутер форвардит `station.play_station` без изменений, разрешения
  station→stream в коде нет. → шаги 2.3, 3.2 (RS-3).
- **F2.** Каталог: `GET /api/v1/catalog/stations` реализован, но отсутствует в
  OpenAPI; browse и search анонимные и возвращают `stream_url`. → шаги 2.1,
  3.1 (RS-1, RS-2).
- **F3.** Voice `/voice/stream` — анонимный поиск станции по транскрипту;
  типизированный `UserIntent` есть, но к voice не подключён; cancel-фрейма
  нет; OpenAPI дрейфует (sample rates, лимиты сессии). → шаги 2.5, 3.3
  (RS-1, RS-4).
- **F4.** Rockmobile: нет UI, отправляющего `station.play_station`; `media.volume`
  жёстко валидируется (min 0 / max 100 / step 1..100, нарушение ломает весь
  снапшот каталога); клиентский deadline 10 с с пометкой Expired. → шаг 5
  (RM-1), фиксация семантики «accepted сразу / result асинхронно ≤30 с» в
  шаге 4.5.
- **F5.** Физическая приёмка DC-018 не закрыта: golden presentations,
  координаты тача после power cycle, offline-переходы. → шаг 6.0 (RE-1).
- **F6.** `esp_audio_codec` ≥ 2.6.0 требует чип ESP32-P4 ≥ 3.0, плата — v1.3.
  → спайк и пин версии в шаге 1.2 (RE-3).
- **F7.** `esp-sr` поддерживает ESP-IDF 6.x только с v2.4.1 и экспериментально.
  → спайк и пин версии в шаге 1.3 (RE-3).
- **F8.** Партиции: factory 3 МиБ без OTA-слотов, бинарь 1.8 МиБ, из 16 МБ
  флеша задействовано ~3 МБ; OTA отсутствовал во всём плане. → шаг 1.1
  (RE-2), шаг 9 (RE-9).
- **F9.** Wi-Fi-онбординг конечного пользователя отсутствует (ssid/пароль в
  sdkconfig — дев-конфигурация). → шаг 9 (RE-9), по умолчанию в скопе.
- **F10.** Ранжированный search на сервере не курсоруется — единый курсорный
  путь был бы новой серверной разработкой. → решение: два пути (шаг 2.1).
- **F11 (найдено при выполнении RE-2, 2026-09-09).** Физический pairing на
  плате никогда не завершался: namespace `rock_auth` в NVS отсутствует (и до,
  и после перепрошивки), живая верификация DC-017 покрывала только Wi-Fi-сканер
  и C6; pairing/WSS подтверждены лишь host-тестами. Локальный sdkconfig без
  Wi-Fi-учёток и `CONFIG_ROCKSERVER_BASE_URL`. → задача RE-11; формулировка
  README поправлена.
- **F12 (найдено при выполнении RE-3, 2026-09-09).** Данные моделей esp-sr
  пакуются в отдельный `srmodels.bin` под партицию `model`, которой нет в
  таблице RE-2 (весь флеш отдан под ota_0/ota_1). RE-8 обязан выбрать:
  урезать OTA-слоты под партицию `model`, встроить модели в app-образ или
  внешний путь (`ESP_SR_EXTERNAL_MODEL_PATH`). Решение влияет на схему
  партиций — чем раньше принято, тем дешевле миграция. → задача RE-8
  (решение), потенциально правка RE-2-таблицы.
- **F13 (найдено при выполнении RE-4, 2026-09-09).** Динамик физически не
  подключён к плате: воспроизведение подтверждено только электрически
  (I2S TX + ES8311 + PA); «акустическая петля» из первого отчёта оказалась
  музыкой в комнате и отозвана исполнителем до приёмки. Акустическая
  приёмка шага 1 (слышимый тон) и замер акустической связи mic↔динамик
  для AEC (нужен RE-8) открыты. → задача RE-12, заблокирована физическим
  подключением динамика владельцем.

## Журнал решений

- **2026-09-09, владелец.** Продукт — standalone RockCast-радио на
  JC4880P443C_I_W: локальное воспроизведение, touch browse/search, управление
  с Rockmobile, wake word `ESP` через существующий голосовой путь RockServer.
  DC-019/DC-020 отложены (нет датчиков); DC-039 выбрана к выполнению.
- **2026-09-09, реворк плана (этот диалог).** Каталог — два пути (browse с
  курсором + search ранжированный, оба ≤20, без stream_url). Дисплейные
  состояния `station_list`/`search`/`loading`/`offline`/`playback_error` —
  локальные UI-состояния, без новых remote presentation types. Семантика
  команд: `accepted` немедленно, `command.result` асинхронно ≤30 с (10 с
  expiry в Rockmobile — норма). OTA и Wi-Fi-онбординг — в скопе по умолчанию,
  владелец может явно отменить. Партиции мигрируются до кода плеера.
- **2026-09-09, владелец.** Порядок изменён: шаг аудио/de-risk выполняется
  первым, до контрактов RockServer, — он не имеет зависимостей и снимает
  главный аппаратный риск. План перенумерован: аудио/de-risk = шаг 1,
  контракты = шаг 2, серверная реализация = шаг 3; шаги 4–10 без изменений.
- **2026-09-09, центр управления.** Отчёт RE-2 принят и проверен по коммиту
  f4cdb16 (dual-OTA 2×0x7F0000, загрузка из ota_0, NVS цел). По находке
  исполнителя зарегистрированы F11 и задача RE-11: до её выполнения RE-1 и
  RE-5 физически невыполнимы. RE-3 и RE-4 от неё не зависят.
- **2026-09-09, центр управления.** Отчёт RE-3 принят и проверен по коммиту
  e868b24. Пины подтверждены; оценка худшего случая из device-control.md
  (~3.8 МиБ) сошлась с фактическим образом (3.90 МиБ, 51% слота). По находке
  исполнителя зарегистрирована F12 (размещение `srmodels.bin`), задача RE-8
  дополнена обязательным ранним решением. Примечание сборки: полная
  параллельная пересборка падает по OOM при -j20 — собирать `ninja -C build
  -j 4` (для будущих сессий).
- **2026-09-09, центр управления.** Отчёт RE-4 принят по коммитам 00070d9 и
  2183e7e — в объёме электрического пути. Первый вариант отчёта содержал
  акустические утверждения; исполнитель сам отозвал их до приёмки (динамик не
  подключён, рост уровня mic был комнатной музыкой) — коррекция
  зафиксирована им же в docs/audio-bringup.md. Остаток приёмки шага 1
  выделен в RE-12 (F13). Замечено: образ вырос 1.79→3.90 МиБ в RE-3
  (спайк с принудительной линковкой esp-sr) и вернулся к 1.86 МиБ в RE-4
  (спайк-заглушка удалена) — это ожидаемо, esp-sr вернётся в образ в RE-8.
- **2026-09-09, центр управления.** Отчёт RS-1 принят и проверен по коммиту
  6eb996f (src/ не тронут, тест 8/8 запущен центром самостоятельно). Решения
  исполнителя сверх инструкции рассмотрены и утверждены: (а) синхронизация
  esp32-manifest и directory-snapshot fixtures — обязательна для RM-1;
  (б) device-search как **GET с query-параметрами** — контраст с публичным
  POST /search, учесть в RS-2 и в firmware (RE-5/RE-6);
  (в) device-каталог без нового scope — достаточно валидной device-сессии;
  (г) planned voice-поля дают окно дрейфа до RS-4 (рантайм с
  deny_unknown_fields их отвергнет) — осознанно; (д) в коммит вошли
  ранее незакоммиченные doc-правки DC-019/020-deferral. Контракты шага 2
  заморожены: RS-2/3/4 реализуют под них, менять — только через центр.
- **2026-09-09, центр управления.** Отчёт RS-2 принят и проверен по коммиту
  4a1612a (тесты device_catalog_api 12/12 и openapi_contract 8/8 запущены
  центром). По открытым вопросам исполнителя: (а) правка сортировки
  in-memory каталога в src/search/mod.rs **утверждена** — трактовка
  «не менять публичные /catalog» как не-нарушенной подтверждается: это
  багфикс, приводящий in-memory режим к семантике Postgres (ORDER BY
  стабильного id) и к документированному stable-ID-курсору, контракт
  публичного каталога не менялся; (б) 403 остаётся зарезервированным —
  ревокация наблюдается как 401; (в) маппинг таймаута device-поиска в 503
  (вместо 504 публичного пути) утверждён, учтён в RS-4.
  **Кларификация для RE-5:** по замороженному контракту плеер получает
  `station.play_stream` (source=rockserver_catalog, эхо station_id,
  stream_uri) под тем же command_id — firmware реализует обработчик
  play_stream, а не play_station; формулировка шага 4 плана
  («implement station.play_station») читается как «сквозной путь от
  play_station», контракт имеет приоритет.
- **2026-09-09, центр управления.** Отчёт RS-3 принят и проверен по коммиту
  e24d00f (контрактные тесты и lib запущены центром). Решения по открытым
  вопросам: (а) предсуществующее расхождение terminal-error payload
  ({code,message} vs схема с request_id+details) решено выправлять В СТОРОНУ
  СХЕМЫ — регистрируется RS-5 (добавить поля на wire); основание: canonical
  fixtures — контракт-оф-рекорд, прошивка толерантна к доп. полям (центр
  проверил: deny_unknown_fields в rock-esp32/src отсутствует), RS-5 обязан
  закрыться до RE-5 и проверить парсер rockmobile; (б) DNS-уровень SSRF —
  ограничение принято: редиректы (≤5) и DNS валидирует стрим-клиент таргета
  (RE-5, bounded); серверный egress-слой — кандидат в backlog-хардненинг,
  отдельной задачей сейчас не заводится.
- **2026-09-09, центр управления.** Отчёт RS-4 принят и проверен по коммиту
  a9dd9cf (voice 9/9 и контракты 8/8 запущены центром). Отступление от
  freeze: схема дополнена VoiceDeviceCommandResult + полным
  VoiceStreamErrorCode — **утверждается задним числом** как поправка RS-4a:
  RS-1 не определял result-фрейм device-voice-флоу (реальный пробел, а не
  каприз), форма чистая (additionalProperties: false, style v1), legacy/
  анонимный путь не тронут, контрактные тесты обновлены. Урок для следующих
  задач: пробел контракта — повод остановиться и запросить решение, но
  формально корректное дополнение с тестами принято. Бонус-улучшение
  принято: из debug-логов Yandex LLM убраны тела запросов с текстом
  пользователя и идентификаторами (усиление F3-приватности). Решение
  «после WS-upgrade таймаут поиска → error-frame search_timeout вместо
  HTTP 503» утверждено (HTTP-статус после upgrade невозможен). Все
  planned-маркеры voice сняты — серверная ветка RS-1..RS-4 закрыта,
  осталась маленькая RS-5 (до RE-5).
- **2026-09-09, центр управления.** RS-5 принята (987967d; полный cargo
  test 206/0 запущен центром; парсер rockmobile подтверждён лично —
  ignoreUnknownKeys=true). Серверная ветка (шаги 2–3 плана) закрыта
  полностью: RS-1..RS-5 done. Разблокирован RE-5 (player MVP); его живая
  end-to-end приёмка ожидает RE-11 (pairing + Wi-Fi) со стороны владельца.
- **2026-09-09, центр управления.** Отчёт RE-5 принят (f5ed186; host-тесты
  10/10 запущены центром). Замечания центра: (а) underruns 52 — только
  пачкой при переключении частоты I2S в первые секунды, в установившемся
  режиме счётчик неподвижен — принято; (б) обнаружен безусловный запуск
  player self-test из main.c при каждой загрузке (assert в продакшн-пути)
  — зарегистрирована RE-13; до RE-12 тон при буте сохраняется намеренно.
  Расхождение ядров: аудио на Core 1, UI/touch/Wi-Fi на Core 0 —
  соответствует замерам RE-4.
- **2026-09-09, центр управления.** RM-1 принята (fb8e3a7; юнит-тесты
  9/9 и 11/11, полная сборка — прогнаны центром). Поздний Succeeded после
  клиентского Expired трактуется как успех с пояснением — соответствует
  семантике «accepted/result асинхронно» из RS-1. Физическая приёмка
  (реальный ESP32 через RockServer с телефона) — после RE-11. Шаг 5 плана
  закрыт в коде; остаются шаги 6–10. Следующие диспатчи без блокеров:
  RE-9 (OTA, зависит только от RE-2), RC-1 (design tokens), RE-13
  (selftest-гейт).
- **2026-09-09, центр управления.** План RE-9 (implementation_plan.md из
  brain-каталога исполнителя, сохранить в docs/ при закрытии задачи)
  утверждён с двумя обязательными правками: (1) убрать
  ROCK_OTA_SKIP_CERT_VERIFY — только пустой TEST_CERT_PEM → cert bundle
  или явный тестовый CA, никаких опций отключения TLS-проверки;
  (2) onboarding-портал защитить одноразовым PIN с LVGL-экрана (открытый
  SoftAP + открытый POST /connect — вектор угона устройства). Мелочи:
  CONFIG_APP_ROLLBACK_ENABLE не существует (оставить только BOOTLOADER_*
  вариант), проверить APSTA+scan на ESP-Hosted 3.0.7, пропускать
  transport-инициализацию в режиме онбординга. Отмечено нарушение
  план-гейта: 712 строк кода написаны до одобрения плана (не закоммичены);
  исполнителю сверить существующий код с утверждённым планом и правками.
- **2026-09-09, центр управления.** RE-9 принята по коммиту e653e17 в части
  OTA: обе обязательные правки проверены в коде центром (skip-verify — 0
  упоминаний; PIN генерируется/валидируется strcmp'ом/в QR/на экране),
  host 10/10 запущен центром, аппаратный цикл OTA 8/8 (загрузка из ota_1,
  PENDING_VERIFY → mark_valid после сети, abort без записи при совпадении
  версий, аудио-соук без доп. underrun). ДВА ПРЕУВЕЛИЧЕНИЯ отчёта
  зафиксированы: (1) «all acceptance criteria respected» — но реальный
  откат плохого образа не демонстрировался (только успешный mark_valid);
  (2) онбординг-флоу с телефона не имеет следов прогона. Остатки → RE-14.
  Мелочь: PIN печатается в serial-лог при генерации — приемлемо (владелец
  с UART-доступом видит и экран), но убрать при случае.

## Правила выполнения и приёмки

- Контракт перед реализацией: RS-1 закрывается до RS-2/RS-3/RS-4.
- rock-esp32: сначала host contract tests (`tests/device_control_contract.rs`)
  и серийная сборка `idf.py`; флеш только после успешной сборки; перед прошивкой
  заново детектить COM-порт; физическая верификация записывается в
  `docs/*-progress.md`.
- rockserver: контрактные тесты, включая `tests/openapi_contract.rs`; после
  реализации — обновить `docs/roadmap/device-control-tasks.md`, `docs/status.md`,
  `docs/tasks.md`.
- rockmobile: сборка + ручной сценарий на физическом ESP32.
- Сквозное правило: никаких секретов, токенов, аудиосэмплов и stream URI в
  логах, коммитах и документах.
- Манифест устройства честный: capability добавляется только после прохождения
  приёмки соответствующим обработчиком на железе.

## Как диспатчить задачу из центра

Исполнителю (суб-агенту в целевом репозитории) передаются:

1. ID задачи и репозиторий (путь).
2. Соответствующий шаг плана `rockcast-device-plan.md` и находки аудита (F#).
3. Приёмка шага как критерий готовности.
4. Требование по завершении: коммиты в целевом репо, записи в его docs,
   отчёт центру управления (что сделано, что проверено, что осталось).

Статусы на доске обновляет центр управления, не исполнитель.
