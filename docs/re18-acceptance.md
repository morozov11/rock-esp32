# RE-18 аппаратная приёмка, 2026-10-16

Стенд: ESP32-P4 v1.3, COM6, ESP-IDF 6.1, одна сеть и тот же RockServer. Измерения взяты из отфильтрованного serial-вывода `tools/re18_acceptance.py`; токены, URL и тела ответов не сохранялись. `connect_ms` включает DNS, TCP и TLS; `wait_headers_ms` отсчитывается от отправки заголовков до их полного приёма.

## До изменения

В `uc15b_bench.log` есть один запрос каталога: от `catalog fetch` до HTTP 200 примерно 2,08 с. Это одиночный замер без разделения на connect/TLS и ожидание ответа, поэтому он не служит медианой или строгим сравнением холодного пути.

## Финальная прошивка

- Холодный REST GET `/health/ready` после перезагрузки: connect/TLS 2883 мс, ожидание заголовков 44 мс, HTTP полностью 2930 мс. Это тот же origin, но другой endpoint; первый каталог уже использует прогретый handle.
- Первый каталог после подключения WSS: HTTP 135 мс, до обновления виджета 165 мс.
- После закрытия REST-сокета при простое: 5 запросов каталога после пауз 300, 90, 90, 90 и 90 с. Все получили HTTP 200, `reused_handle=1`, `stale_retry=0`.

| Пауза | Connect/TLS, мс | Ожидание заголовков, мс | HTTP полностью, мс | До обновления виджета, мс |
| ---: | ---: | ---: | ---: | ---: |
| 300 с | 374 | 188 | 614 | 823 |
| 90 с | 135 | 164 | 336 | 511 |
| 90 с | 145 | 118 | 314 | 411 |
| 90 с | 188 | 115 | 340 | 409 |
| 90 с | 97 | 105 | 234 | 415 |

Медиана connect/TLS — **145 мс**, медиана до обновления виджета — **415 мс**. Холодный connect/TLS был 2883 мс. При пяти повторных connect использовался тот же handle и сохранённый ticket (`save_client_session`); ускорение в 7,7–29,7 раза по сравнению с холодным TLS на том же стенде служит сопоставимой трассой фактического resumption. Серверная метка принятия ticket и отдельный mbedTLS debug не снимались.

Предыдущая аппаратная итерация выявила закрытый сервером keep-alive: первый GET после 300 с завершился `ESP_ERR_HTTP_FETCH_HEADER`. Однократный GET-повтор восстановил запрос за 437 мс до обновления виджета; финальный вариант профилактически закрывает сокет после 60 с простоя и не выдаёт этой ошибки после 300 с.

На промежуточной прошивке пять повторов каталога: 295, 278, 197, 191 и 298 мс до обновления виджета (медиана 278 мс). Поиск: HTTP 2157 мс, в том числе ожидание заголовков 2151 мс, виджет 2469 мс. Следующая страница: HTTP 72 мс, виджет 197 мс. На сборке перед финальным изменением пять повторов дали медиану 253 мс, поиск и пагинация получили HTTP 200.

Плановое обновление токена на финальной прошивке: REST POST вернул 200 (`reused_handle=1`, connect/TLS 132 мс, HTTP 272 мс). Следующий GET каталога с текущим bearer вернул 200 по тому же открытому соединению, до обновления виджета 471 мс. Значения bearer не выводились и не сохранялись.

Финальный короткий прогон после обновления токена: пять повторов каталога 298, 238, 632, 223 и 767 мс до обновления виджета (медиана 298 мс); поиск HTTP 200 за 3294 мс до виджета, из них 2973 мс ожидание заголовков; следующая страница HTTP 200 за 186 мс до виджета.

## Ограничения проверки

Метка «до обновления виджета» ставится после синхронной LVGL-функции под её lock; физический scanout дисплея отдельно не замерялся. Холодный каталог без предварительного health-запроса не получен; холодный путь сравнивается только косвенно. Принудительный 401, проверка сервером точного значения нового/отсутствующего bearer и управляемая сетевая ошибка не выполнялись.
