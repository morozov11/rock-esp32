# RE-3: спайки аудио/SR-компонентов (2026-09-09)

Build-only спайк по шагам 1.2–1.3 плана [`rockcast-device-plan.md`](rockcast-device-plan.md)
(находки аудита F6, F7). Цель — проверить совместимость компонентов с платой
и ESP-IDF 6.1.0 и запинить версии до аудио-пути (RE-4). Рантайм-поведение
прошивки не меняется: ни один API компонентов не вызывается, аудио не
заводится.

Окружение: плата JC4880P443C_I_W v1.3, чип ESP32-P4 ревизии ниже v3.0
(`CONFIG_ESP32P4_SELECTS_REV_LESS_V3=y`, `CONFIG_ESP32P4_REV_MIN_100=y`),
ESP-IDF 6.1.0, сборка `idf.py --no-ccache build` (см. «Инциденты сборки»).

## Выбранные версии (main/idf_component.yml)

| Компонент | Версия | Обоснование |
| --- | --- | --- |
| `espressif/esp_codec_dev` | `1.6.2` | Последняя стабильная 1.6.x (пре-релиз 2.0.0-beta4 не рассматривался). Манифест: `idf >= 4.0` без верхнего порога — собирается на IDF 6.1. Существенно для RE-4: 1.6.0 добавляет счётчик ссылок для шаринга одного физического кодека между инстансами, 1.6.2 — настройку тактовой I2C (`clock_speed_hz`), что нужно на общей шине I2C1 с GT911. |

Обновление на 2.6.x возможно только вместе с платой на чипе P4 >= 3.0 (сборки IDF для v1.x и v3.x взаимоисключающие). |
| `espressif/esp-sr` | `2.5.3` | Находка F7. Поддержка IDF 6.x: появилась в v2.4.1 («Experimental support esp-idf v6.0»), v2.5.0 — «Resolve the incompatibility between Kconfig and IDF v6.1», v2.5.3 — актуальная (фикс утечки памяти wakenet10). [esp-adf-libs](https://github.com/espressif/esp-adf-libs) (esp_audio_codec),
[esp-adf](https://github.com/espressif/esp-adf) (esp_codec_dev) и

## Kconfig esp-sr

Записано в трекаемый `sdkconfig.defaults`:

- `CONFIG_SR_WN_WN9_HIESP=y` — стоковая модель wake word **wn9 «Hi ESP»**
  (единственная выбранная; все прочие `SR_WN_*` по умолчанию `n`);
- Multinet отключён значениями по умолчанию: `SR_MN_CN_NONE`, `SR_MN_EN_NONE`;
- AFE и подавление шума — значения по умолчанию: `AFE_INTERFACE_V1`,
  `SR_NSN_WEBRTC`, `SR_VADN_WEBRTC`, `MODEL_IN_FLASH`.

Линковка в образ обеспечена `main/audio_spike.c`: глобальная таблица
`rock_re3_component_roots` ссылается на публичные API (`esp_afe_handle_from_config`,
`esp_srmodel_init`, `esp_codec_dev_new`, `esp_codec_dev_read/write`,
`esp_audio_dec_open`, `esp_audio_simple_dec_open`), а флаг
`LINKER:-u,rock_re3_component_roots` в `main/CMakeLists.txt` вытягивает таблицу
из `libmain.a` — без корневой ссылки `--gc-sections` выкидывает компоненты
целиком (проверено: без флага образ вырастал лишь на ~2.4 КиБ). Таблица не
имеет конструктора и никогда не читается — рантайм не меняется.

## Верификация

- Полная сборка `idf.py --no-ccache build` — `Project build complete`
  (из-за OOM компилятора на esp-dl сборка велась `ninja -C build -j 4`,
  см. ниже; это та же цель ninja, что запускает idf.py).
- Host contract tests: `cargo test --target x86_64-pc-windows-msvc
  --test device_control_contract` — **6/6 passed**.
- Sanity-прошивка на плате (COM6): запись otadata + приложения в ota_0
  (0x20000–0x406fff), хэши сошлись, NVS не стирался. В 45-секундном
  сериал-логе после сброса: `Loaded app from partition at offset 0x20000`
  (загрузка из ota_0), `esp-hosted fw versions: host=3.0.7 coprocessor=3.0.7
  (match)`, интерактивный Wi-Fi-сканер находит 8–9 точек и ресканит каждые
  10 с, ST7701/LVGL/GT911 инициализируются как раньше. Заодно подтверждён
  чип: `ESP-ROM:esp32p4-eco2` — ревизия ниже v3, как и предполагал выбор
  esp_audio_codec 2.5.0. Аудио-поведение не проверялось и не должно
  меняться (микрофон/спикер — RE-4, wake word — RE-8).

## Инциденты сборки (для будущих сессий)

1. Component manager упал с `WinError 2` при копировании файлов моделей
   esp-sr из кэша в `managed_components` (частично скопированный каталог).
   Лечится удалением частичных каталогов в `managed_components` и
   перезапуском сборки; кэш при этом цел.
2. `cc1plus.exe: out of memory` на C++-файлах esp-dl: ninja по умолчанию
   гонит `-j20` (20 логических ядер), а свободный commit-лимит машины в этот
   момент был ~7 ГиБ. Стабильно собирается с `ninja -C build -j 4` — у
   `idf.py` в 6.1 опции `-j` больше нет.
3. Git Bash/PowerShell-обёртки: `export.bat` и `idf.py` отказываются работать
   при унаследованных `MSYSTEM`/`TERM` — в PowerShell-команде их надо
   удалять (`Remove-Item Env:MSYSTEM …`). Оболочка `espidf_source.bat`
   из Git Bash не запускается вовсе; использовать профиль
   `C:\Espressif\tools\Microsoft.v6.1.PowerShell_profile.ps1`.

## Известные оговорки и открытые вопросы

- **Статус esp-sr на IDF 6.x.** Changelog 2.5.0 закрывает несовместимость
  Kconfig с IDF v6.1, и прекомпилированный набор `esp32p4_less_v3_idf6`
  существует именно под нашу конфигурацию, но Espressif не публикует явную
  матрицу поддержки; аудит F7 называл поддержку IDF 6.x экспериментальной.
  Физическая проверка AFE/WakeNet на плате остаётся за RE-8.
- **Данные модели wake word не входят в образ приложения.** esp-sr упаковывает
  выбранные модели (`wn9_hiesp`) в отдельный `srmodels.bin` и прошивает их в
  партицию `model` (скрипт `model/movemodel.py`); без такой партиции шаг
  пропускается — сейчас код движков WakeNet/AFE в образе есть, а файлов модели
  нет. Наша RE-2-таблица отдаёт весь флеш под ota_0/ota_1 (0x1000000), места
  под партицию model без урезания слотов нет. RE-8 должен выбрать: урезать
  OTA-слоты и завести партицию model (модели общие для слотов — усложняет
  OTA), встроить модели в образ приложения или грузить по внешнему пути
  (`ESP_SR_EXTERNAL_MODEL_PATH`, появилось в esp-sr 2.4.1). Это главный
  открытый вопрос спайка.
- esp-dl 3.3.11 — тяжёлый C++-компонент (транзитивно от esp-sr); в итоговый
  образ попадает только используемая часть, но он заметно увеличивает
  требования к памяти сборки (см. инцидент 2).
- Замер размера — это линковка движков ровно с одним выбранным Kconfig;
  реальный аудио-путь (RE-4) добавит PCM-буферы/задачи, но они в RAM, а не во
  flash. Проверка микрофона и спикера физически — RE-4, в RE-3 намеренно не
  выполнялась (другое рантайм-поведение запрещено задачей).
